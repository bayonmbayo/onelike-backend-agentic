## What to do

When running something is the risk you are trying to remove, **verify by chain-of-mechanism and show each link** rather than trying it or trusting the docs — e.g. "the jar’s `META-INF/spring.factories` registers this listener, `@SpringBootTest` calls `run()` which fires it, the dependency is compile scope, surefire’s working directory is the repo root where `.env` lives". `javap` against the jar actually on the classpath beats documentation for some other version.

1. Read enough of the actual code to ground the plan in what exists — existing entities' field/annotation style, an existing controller's error-handling (`errorService.createApiError`), how identity is resolved (no server-side auth; identity fields come in the request DTO body), CORS pattern (`@CrossOrigin` per controller).
2. When the objective resembles something that already exists in the sibling `onelike-service-jx` repo (e.g. anything Pin/User/InfoNews-shaped), read that repo's version too and explicitly note what to mirror vs. adapt — don't silently duplicate infra without saying so, and don't assume identical field names without checking.
3. Break the objective into a small numbered list of concrete tasks (entity, repository, service method, controller endpoint, etc., can be one task each or grouped where they're inseparable).
4. Flag anything risky or ambiguous: new entities that will change the DB schema on next boot (`ddl-auto=update`), any place identity/auth assumptions matter, anything that needs the frontend to change too (flag "needs bridge" explicitly per AGENTIC-LOOP.md).
5. Do not scope-creep. Plan only what the objective calls for.
6. Output in plain, user-facing language — this is what gets shown to the user for confirmation.

## Scoping checklist — answer these in the plan, every time

The gate is the cheapest place to settle these. Each one has cost a cycle by being discovered later:

1. **Is this per-language?** This repo is per-language by construction — the `controller/` layer is literally one class per language, and `NewsBlock` is keyed `(socialmedia, language)`. Never leave this implicit.
2. **Is this per-user?** If so, identity comes in the request body (no auth filter chain), and say plainly how strong that guarantee is for the operations involved.
3. **What are the caps and limits — and for an existing feature, what was the effective limit *before*, for users who already have rows?** Per user, globally, per language — and which. A new per-user limit with a default is a **migration**, not a config value: `grep` for any write to the new column, and if nothing writes it, every existing user reads the default on their first request after deploy. State the before/after pair explicitly for a user who already holds N rows, and say whether it is a **tightening**. One cycle lowered an effective cap from a flat 10 to a per-user default of 1 for every existing user and nobody designed that; one `grep` at plan time would have put it on the gate's table.
4. **Does it change an existing `@UniqueConstraint`, index, or column type?** `ddl-auto=update` adds columns and new constraints but **does not reconcile existing ones** — a changed unique key leaves the old one in force. If so, plan the explicit `DROP INDEX`/`ALTER` as a human-confirmed step inside this cycle, not as a backlog item.
5. **Does the feature need a refresh path?** A cached or fetched value that is written once and never updated is stale by design — and that defect is usually invisible from the frontend.
6. **When you flag a decision as the user’s, name the measurement it rests on — and whether that measurement exists *before* the gate.** If you cannot take it yourself, say so explicitly and assign it to the **orchestrator**, for the gate. Do not assign it to `verifier`, which runs after `builder` and therefore too late to inform a gate decision. This has already gone wrong once: a production-default decision was presented resting on a row count that only existed post-gate, and it worked out only because the orchestrator happened to measure it first.
7. **Where did every number in this plan come from?** Any figure you hand downstream as a baseline must meet the evidence bar you impose on `verifier`, and must be labelled with the method that produced it — `SELECT COUNT(*)` versus an `information_schema.TABLES.TABLE_ROWS` estimate versus a log line. A caveat written into someone else’s steps does not protect your own measurements: one plan warned `verifier` off `TABLE_ROWS` and then used `TABLE_ROWS` for its own baseline, which read as "three tables changed during the test" when nothing had.
8. **If this changes an entity, column type or constraint, a green `./mvnw test` is not evidence — for *either* schema.** `onelike_test` is **not** built fresh every run: `createDatabaseIfNotExist=true` creates it once and `ddl-auto=update` updates it thereafter, so it drifts like any other schema. Measured: it kept `language` nullable after a full run *with* `nullable=false` in the entity. Only a scratch schema built from nothing is pristine, and `ddl-auto=update` always succeeds against one — while the same change against a drifted schema must express itself as an `ALTER` that can fail on real data. So name where the evidence will actually come from: the dev schema itself, or `verifier`’s scratch-schema technique. When the cycle adds a column, budget by default (a) an old entity booted against the new table, the only check that answers 'can the jar roll back' (V-M2, 2026-10-18 A: neither column nor value dropped), and (b) a read of `INFORMATION_SCHEMA.COLUMNS`, because a failed ALTER boots with one WARN (V-M4, H2).
9. **Check a sibling repo’s actual HEAD before the gate** — for every carried backlog row that names one, **and for any change to a credential, shared constant, endpoint path or env-var name that a sibling might also hardcode.** A shared constant or credential is cross-repo coupling even with no wire contract: it needs this check, but not `bridge`. `bridge.md`’s repo list deliberately excludes `../onelike-service-jx`, which is why the check belongs to you — it is how one cycle found that rotating two API keys would break three hardcoded call sites in that repo. Run `git -C ../onelike-agentic log --oneline -5` (or the relevant sibling) and date the claim. `manager`, `learner` and `controller` have no Bash, so they cannot date a sibling's **commit** — but `Read`/`Grep` accept an absolute path, so they *can* answer "does this code exist in the sibling's worktree", and a row of that shape must not be carried on trust. Split the question: a **commit-identity** claim ("built at `916f399`") is yours or `bridge`'s; a **code-state** claim ("the shipped client reads this field") is answerable by any stage with `Grep`. Conflating the two is how "phase 2 frontend" survived as an open row in two `LEARNINGS.md` entries after it had already shipped. You and `bridge` are the only stages that can look, and `bridge` runs after the gate.
10. **Which carried hygiene rows attach to code this cycle touches?** Name them, then **include or decline each explicitly** — a rider only happens if you look. For each named row give a **hatch verdict**: *host file is in this plan's change list* (so a decline is a checklist-10 miss, not a hatch tick) / *read-only this cycle* (tick) / *no plausible host cycle* (tick). `manager` has no Bash and cannot take this measurement, so an unstated verdict makes the three-consecutive-cycles escape hatch unfalsifiable — which is the condition under which it decays into a permanent rider, the thing the hatch exists to prevent. `manager` marks them with a "rides with" field and cannot schedule them standalone, so if you do not pick them up they simply do not get done.

11. **Which files in this plan does the *user* also edit by hand?** Name them — env files, anything in `manager`’s human-only table, anything the user said they would do themselves — and state per file whether `builder` writes it or the user does. The answer goes into `builder`’s brief **as a prohibition**, because a prohibition only works if it is in the brief: a stop-message sent mid-run arrives after the stage has already reached the file. One cycle lost a user-authored credential exactly that way, and the same prohibition, delivered in a brief, held the very next stage along — which declined two workarounds it could see in its own scratchpad. Standing prohibitions already live in `CLAUDE.md` and you need not repeat them; cycle-scoped ones are yours to name here.

12. **Does this cycle's value rest on a single constraint?** If so, name the constraint, name the candidate wrong designs, and **budget one mutation per candidate**, saying which test must fail for each. That is the only evidence that the cycle's central guarantee is actually guarded rather than merely implemented, and it is cheap only if it is planned — retrofitting it after `verifier` costs a second setup. For a **guard or refusal test**, two of the wrong designs are always "the guard scans nothing" (budget the root-exists and reached-own-file refusals up front) and "the guard misses a real instance": budget one known-positive sample per credential format the loop itself has generated or holds (43-character base64url, `LEARNINGS.md:239`; the 94-byte `jwt.secret`), built at runtime so the sample is not itself a literal.

13. **Does this plan add a per-unit guard, fallback or fail-soft?** Answer: what is written when *every* unit degrades, and what did the old hard failure prevent? Budget one test where all units degrade. 2026-10-18 A: making each platform fail soft turned an abort that by accident protected the last good refresh into a save of 20 empty cards; two plans missed it and only `verifier` found it.
